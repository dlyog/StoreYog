# What Our Experience Says About MCP Tool Calling for Small Businesses: An Intelligent Router with a Small Model Is All You Need

**Tarun Kumar Chawdhury**
DLYog Lab Research Services LLC

2026-10-23

## Abstract

Small businesses could benefit from voice assistants that act on their own records: a grocery owner asks where the jaggery is, how much rice is left, or to draft a restock, and the assistant answers from the store's actual inventory. The Model Context Protocol (MCP) gives such assistants a standard way to call tools, but the usual recipe, in which a large language model reads every tool schema, plans calls, writes their arguments and composes a reply, assumes a capable and costly model. We report what we learned building StoreYog, a voice assistant for a small Indian grocery store built for an Alexa+ hackathon and backed by a self-hosted MCP server, and we compare three ways of turning a spoken request into MCP tool calls on the same store and the same 30-turn benchmark: (1) Gemma 4 E2B with its native function-calling format and all tool schemas in the prompt; (2) an intelligent router, in which the same Gemma model only chooses one of eleven numbered actions from in-context examples and returns a one-line JSON, while application code runs a fixed, audited sequence of MCP calls and builds the reply from real results; and (3) a 350-million-parameter OPT model that we fine-tuned on 19,408 synthetic conversations generated by running the real MCP server. Over three runs on the live deployment, the router answered 29 of 30 turns correctly in every run (96.7%), the fine-tuned small model 27 of 30 (90.0%) with the lowest latency (median 0.74 s per turn), and native tool calling 14.7 of 30 on average (48.9%). Every turn passed the same responsible-AI prompt guard, which reached 99.67 F1 on a 250-prompt moderation set. Our experience suggests that, for narrow business domains, a carefully designed router over a small model is enough, and that the hard parts belong in code.

## Introduction

Large language models (LLMs) can now call external tools, and the Model Context Protocol (Anthropic, 2024) has made those tools portable: a store exposes its inventory, sales and ordering functions once, and any MCP client can use them. For a small business, however, the default way to use these tools is a poor fit. The common pattern gives a general-purpose model all tool definitions and lets it plan multi-step calls. That needs a large model with a long context, adds latency to every spoken turn, and leaves correctness to the model's judgment at each step, including steps that change stock or place orders.

We built StoreYog for the Alexa+ hackathon: an owner workspace, a customer shelf finder and a voice assistant for "Little India Grocery", a fictitious store with 38 products and synthetic sales, all sharing one store-scoped SQLite ledger behind an authenticated MCP server. The voice assistant runs in a web simulator of an Echo Show and, separately, as a classic Alexa custom skill on a real Echo. Building it forced a practical question that much of the tool-calling literature answers on general benchmarks: what actually works when the tools are few, the domain is narrow, the owner speaks casually through imperfect speech-to-text, and the model must run on hardware a small business, or its software vendor, can afford?

This paper reports what we found. We implemented three ways to map an owner's request to MCP tool calls and ran them side by side on the same live store, behind the same safety guard, with every prompt, response, tool call and executed SQL statement recorded in the store's audit log. The three approaches differ in how much they ask of the model. Native tool calling asks the most: choose tools, fill arguments, chain calls and write the answer. The fine-tuned small model learns the same job from synthetic data. The router asks the least: pick one action and name the product, and let code do the rest.

Our main finding is that asking less of the model is what works. A 2-billion-parameter model used as a router, with eleven numbered actions and about two dozen in-context examples, was almost always right, while the same model given the full tool schemas was right only about half of the time. A 350-million-parameter model trained on the store's own tool traces came close to the router and was the fastest. We describe the systems, the data and the benchmark, analyse the failures, and discuss what this means for building assistants for small businesses.

## Literature Review

Tool use by language models was established by Toolformer (Schick et al., 2023), which taught a model to insert API calls into its own text, and by ReAct (Yao et al., 2023), which interleaves reasoning steps with actions. Gorilla (Patil et al., 2023) fine-tuned a model to write API calls from documentation, and ToolLLM (Qin et al., 2023) built ToolBench, a large instruction set over real APIs that remains a standard benchmark. The Berkeley Function Calling Leaderboard (Patil et al., 2025) evaluates serial and parallel calls and multi-turn agentic use; its authors report that frontier models handle single-turn calls well while memory, dynamic decisions and long-horizon reasoning remain open problems. These results describe what large models can do with general tool sets; our setting has few tools, a narrow domain and spoken, noisy input.

A second line of work shows that small models can be strong tool callers when trained for the task. Octopus v2 (Chen and Li, 2024) represents each function as a dedicated token, turning function selection into a single-token classification; its 2-billion-parameter on-device model is reported to beat GPT-4 on accuracy and latency for Android APIs while using 95% less context. TinyAgent (Erdogan et al., 2024) fine-tunes 1.1B and 7B models for function calling at the edge, using tool retrieval to shorten prompts, and reports parity with GPT-4-Turbo on its task. Most directly related to our small model, Jhandi et al. (2025) fine-tuned facebook/opt-350m (Zhang et al., 2022) with targeted supervised fine-tuning and report a 77.55% ToolBench pass rate, above much larger baselines; we follow their training recipe. Belcak et al. (2025) argue more broadly that small language models are sufficient, better suited and cheaper for most agent calls, and that agentic systems should be heterogeneous, calling a large model only when needed.

A third line concerns routing and tool selection. RouteLLM (Ong et al., 2024) learns to route each query between a strong and a weak model, cutting cost by more than half without losing quality. For MCP specifically, RAG-MCP (Gan and Sun, 2025) shows that tool-selection accuracy collapses as the number of tool schemas in the prompt grows ("prompt bloat"), and that retrieving only the relevant tool first raises accuracy from 13.62% to 43.13% while halving prompt tokens. Our router can be read as the limiting case of these ideas for a small business: instead of retrieving among many tools, the domain is compressed into a short, numbered list of business actions, and the model's only job is classification by in-context learning (Brown et al., 2020), close in spirit to Octopus's functional tokens but without training.

Finally, safety. Llama Guard (Inan et al., 2023) introduced an LLM-based input/output safeguard with a category taxonomy, and our earlier work (Chawdhury, 2024) showed that a general LLM with a carefully crafted system prompt can act as a content moderator, reporting 98.39 F1. We reuse that guard design for every request in all three modes.

## Methodology

### Experimental Setup

The store is the synthetic Little India Grocery: 38 products with units, shelf locations, published shelf photos, selling prices and costs, 40 synthetic sales receipts for the day and a seven-day sales history. The MCP server (MCP 2025-11-25, stateless Streamable HTTP) exposes seven owner tools bound to the store by its credentials: `get_inventory`, `get_todays_transactions`, `reconcile_inventory`, `update_inventory`, `place_reorder`, `send_inventory_report` and `send_sales_report`. The web simulator adds three simulator tools that act in the browser: `play_demo` (the demo film), `play_guide` (33 original audio guides on inventory, small business and nutrition) and `ask_general` (general questions answered by the general LLM). The application runs on one Linux server; Gemma 4 E2B (google/gemma-4-E2B-it) is served by a Hugging Face Transformers server on a separate lab GPU host; the small model is served on an NVIDIA DGX Spark (GB10) on the same local network.

All three modes share the same server, store, audit, guard and server-side rules:

- The store identity comes from server credentials, never from model text.
- `update_inventory` runs only when the owner's words ask for a count change with a number, and `place_reorder` only when they ask to order or restock (or narrow a draft just offered).
- The model can only draft an order; a fresh, explicit "yes" from the owner to the exact draft is handled in code and is the only way to confirm.
- Sales email is blocked in the public demo; inventory counts in replies come from MCP results.

The three modes are:

- **Mode A, native tool calling.** Gemma receives the store assistant's system prompt, tool rules and all MCP tool declarations in Gemma 4's native format, and returns tool calls in that format. The application executes each call and appends the result; the loop allows up to six steps, with nudges when the model describes a step instead of calling it. Temperature 0.1.
- **Mode B, intelligent router.** One Gemma call per turn, temperature 0. The prompt (about 5,000 characters) contains the store's metadata (name, owner, the current product list, the last product discussed), eleven numbered actions with one-line descriptions (0 general, 1 find_product, 2 list_products, 3 todays_sales, 4 store_health, 5 low_stock, 6 draft_restock, 7 update_count, 8 play_demo, 9 play_guide, 10 email_report), 26 in-context examples and the responsible-AI rules. Gemma returns one line of JSON with the action and its arguments. Code maps the action to a fixed sequence of MCP calls, grounds the product in the owner's words, and builds the spoken reply from the real results; action 0 goes to the general assistant.
- **Mode C, fine-tuned small model.** Our OPT-350M fine-tune (v6) uses a compact one-line protocol (`### Catalog:`, `### Owner:`, `### Call:`, `### Result:`, `### Answer:`). The application runs each call it emits, appends a one-line summary of the result and asks for the next line, up to six steps; a number or product fact stated before any tool ran is re-asked with the line forced to start as a call. Greedy decoding.

### Baseline Data Generation

The small model's training data was generated by running the real MCP server in-process against a throwaway copy of the synthetic database, so every tool result in the data is genuine. Scenario generators cover where-is, counts, availability, prices, follow-ups, products not carried, store health, alerts, restock drafts (all low items, only named items, explicit quantities), declines, count updates (reconciling first when needed), reports, the demo film, audio guides, general questions, reactions such as "Oh great." that must not call any tool, and greetings. Requests are varied as speech-to-text would produce them: wake words, fillers, lower case without punctuation, "dahl"/"daal", and Hindi grocery names (haldi, gur, jeera). About half the examples carry one or two unrelated earlier turns. Four products are held out of training to measure generalisation. In version 6, 85% of the examples run on their own randomised store, with stock counts, selling prices, unit costs and shelf locations reshuffled, so that copying from the tool result is the only way to be right. Training followed Jhandi et al. (2025): TRL supervised fine-tuning, learning rate 5e-5, 100 warm-up steps, effective batch 32, gradient clipping 0.3, weight decay 0.01, bf16, three epochs, 43 minutes on the DGX Spark.

The router needs no training data. Its 26 in-context examples are written by hand, two or three per action.

### API Workflow

1. The owner speaks; Whisper converts speech to text (the benchmark sends text directly).
2. The prompt guard checks the request; an unsafe request receives a short spoken refusal and nothing else runs.
3. Server code handles what needs no model: the launch phrase, and "yes"/"no" to a pending draft.
4. The selected mode maps the request to tool calls; the server enforces the write and approval rules on every call.
5. Model-written replies are checked by the guard before they are spoken; the browser plays any shelf photo, film or audio guide after the reply.
6. Every model request and response, tool call, result and executed SQL statement is stored in the store's audit with a shared conversation identifier and the mode that produced it (`gemma-router`, `storeyog-small`, `gemma`, `classic` or `scripted`); each turn is also logged with its mode, latency and outcome. (The mode column was added to the audit tables after the benchmark runs; for those runs the mode comes from the per-turn log, joined by conversation identifier.)

### Evaluation Metrics

- **Benchmark pass rate.** Thirty owner turns, written for this study and not used during development, run in order in one session (later turns refer to earlier ones), across 15 categories: product lookup with speech-style wording and Hindi names (7), not carried (1), catalog (1), sales (1), store health (1), alerts (1), restock (2), decline (1), approval (1), count update (1), reaction (1), media (4), general knowledge (2), greeting (1) and responsible AI (5). Each turn has a declarative, machine-checked expectation over the tool calls, arguments, results, media and reply, published with the data. Spoken numbers ("twenty-eight", "six dollars") count as numbers. Each mode was run three times on the live deployment.
- **Latency.** Wall-clock time per turn seen by the client over the public internet, including the guard, MCP calls and model calls; and model-call durations from the audit log.
- **Small-model step accuracy.** On 600 held-out conversations: exact first tool call (name and arguments) on seen and held-out products, and answer correctness after tool results.
- **Guard quality.** Accuracy, precision, recall and F1 with "unsafe" as the positive class, on a set split like Chawdhury (2024): 100 safe prompts (50 store requests, 25 everyday questions, 25 harmless store questions with alarming words) and 150 unsafe prompts (25 in each of six categories), plus 25 prompt-injection attempts reported separately.

## Experiments and Results

### Baseline Data and Prompt Generation

Version 6 of the small model's data has 19,408 training and 2,880 evaluation conversations: where-is 3,443, count 3,434, available 3,436, price 2,108, follow-up 1,199, not carried 1,112, chat 1,336, update 912, reaction 720, restock 744, shelf 701, alerts 443, health 432, decline 373, order 358, narrow 336, guide 325, list 271, general 188, sales 152, demo 141, report 118, broad 6. The 30 benchmark prompts and their expectations are in `research/benchmark-prompts.json`; the guard set is in `research/guard-eval-set.json`.

### Experiment Setup

The benchmark ran on 2026-10-23 against the public deployment (https://storeyog.dlyog.com) with the store reset before each session. Each mode received the same 30 turns in the same order, three times. One additional attempt stopped on the client side after its first mode and was rerun; its completed session is kept in the turn log but not scored. A first run with a scorer that required digits is also published, because it under-counted native tool calling, which speaks numbers as words.

### Quantitative Results

Benchmark, three runs per mode (30 turns each):

- **Mode B, router:** 29, 29, 29 → **96.7%**; median turn 1.09 s, 90th percentile 1.42 s.
- **Mode C, small model (v6):** 27, 27, 27 → **90.0%**; median turn **0.74 s**, 90th percentile 1.11 s.
- **Mode A, native tool calling:** 15, 14, 15 → **48.9%**; median turn 1.88 s, 90th percentile 3.92 s.

Every mode passed all five responsible-AI turns in every run except the small model on "Does ghee cure diabetes?" (below). The router and the small model were fully deterministic across runs; native tool calling varied by one turn.

Model-call durations from the audit log (median per call, server-side): guard 142 ms; router 519 ms; small model 193 ms per step; Gemma tool-loop and general-answer calls 714 ms.

Small-model step accuracy on 600 held-out conversations (exact first call):

- v5 (memorised store, 14,817 conversations): seen products 238/299 (79.6%), held-out products 115/385 (29.9%).
- v6 (randomised stores, 19,408 conversations): seen products 214/308 (69.5%), held-out products 196/361 (**54.3%**).
- Answer steps after a tool result: 1,010 of 1,269 steps correct overall in v6; almost every answer step was correct.

Prompt guard (Gemma 4 E2B), 250 paper-comparable prompts (identical for guard prompt versions 1 and 2):

- Accuracy 99.6, precision 100, recall 99.33, F1 **99.67** (TP 149, FP 0, TN 100, FN 1).
- All 25 harmless questions with alarming words passed (no false positives).
- Prompt injection: 19 of 25 flagged with version 1, 20 of 25 with version 2.
- Owner requests about their own data (15, added after the live session): 11 passed with version 1, 14 with version 2.

### Qualitative Analysis

**Native tool calling fails at what small businesses need most.** Its 16 consistent failures fall into four groups. (1) Speech and vocabulary: it searched for "haldi", "gur" and "chana dahl" literally and reported them missing, although turmeric, jaggery and chana dal were in stock. (2) Multi-step chaining and unverified claims, the most serious group: for "Order more toor dal only" it called `reconcile_inventory` and then described a draft it never created, quoting a different total in each run ($210, $102 and $124.70; the store's own draft for the same request is $210); for "12 bottles of mustard oil" it looked the product up and stopped, once with an empty reply and twice by describing an order without drafting it; for "We actually have 15 bags of atta" it looked the product up and said "I have updated the stock" in all three runs without calling `update_inventory`. A store owner would have believed that changes had been made. (3) Approval: because no draft existed, "Yes, place the order" had nothing to approve. (4) Missing capabilities: in this mode only the MCP tools were declared, so the film and audio guides were unreachable (this mode was not given the simulator tools; excluding the four media turns it scored 14.7 of 26). It also answered "What is the capital of Japan?" with "I do not have a tool to look up geographical information."

**The router's only miss is context.** "Another one." after a business tip was routed to the general assistant, because the router sees the last product discussed but not the last action. Every product question passed, including Hindi names and "dahl", because the router maps the spoken word to the catalog in one step and code grounds it against the owner's words.

**The small model is fast and reliable on store operations, weaker at the edges.** It passed every lookup, restock, update, approval and decline in all runs. Its three misses are outside the store: "Which of our foods has the most protein?" became a stock search for "protein", "What spices go into a masala chai?" became a lookup of Masoor dal, and "Does ghee cure diabetes?" became "Yes. Ghee is … in stock." The last is a responsible-AI failure that the output guard did not catch, because the guard judged the reply alone, without the question.

### Live Tester Session

After the benchmark, the first author used the deployed simulator by voice for about eleven minutes, switching between the three modes with the page's mode selector: 11 turns in the router, 16 in the small model and 15 in native tool calling, all in one conversation. Speech went through Whisper, so the requests include real transcription errors ("doll" and "dull" for dal, "Turdal" for toor dal, "otta", "ata" and "auto" for atta) and utterances split in the middle by a pause. Every model call and tool call was recorded with its mode. The session was unscripted; we report it as observed, before the fixes that followed it.

- **Router (11 turns):** 8 handled correctly, including "where is the doll?" (mapped to Toor dal), the demo film, the product list, a protein guide and "What is the otta?" (answered by the general assistant as whole-wheat flour). Two legitimate requests were blocked by the guard: "can you tell me my latest inventory report?" and "check my latest inventory and send me an email". One request, "tell me about doll. Give me some tip.", played the first inventory guide rather than the dal guide.
- **Small model (16 turns):** 6 handled correctly (catalog, a not-carried item, rice, demo, a business tip, rice again). It mapped "dull", "doll", "2 doll" and "doll d a l" to Dahi four times in a row, did not find "Turdal", "otta" or "ata", and followed a pause-split "play some tip on … inventory management" as two requests. When the fragment "carry out." arrived, it tried to draft a restock; the server refused the write because the owner had not asked for one, and the assistant replied that nothing had changed.
- **Native tool calling (15 turns):** 5 handled correctly and 2 asked a reasonable clarifying question (doll: Dahi or Dal?). It did not map "auto" or "ATA" to atta, said "I have listed all thirty-eight items" without listing them, and answered all five requests for the demo or a tip with "I do not have a tool".

Three changes followed directly from this session. First, the guard prompt: our version 1 extended the published template (Chawdhury, 2024) with "no attempts to … obtain private data", which Gemma applied to the owner's own reports. Version 2 says that the user is the signed-in owner and that requests about their own store's stock, sales, orders and reports, including emailing their own reports, are safe, while passwords, keys and another store's data remain unsafe. On 15 owner-data requests (including the two above), version 1 passed 11 and version 2 passed 14; on the 250 paper-comparable prompts both scored 99.67 F1, and prompt-injection recall rose from 19 to 20 of 25. Second, a shared correction of observed mishearings ("dull", "doll", "dhal" → dal; "Turdal", "tur dal" → toor dal; "otta", "ata" → atta) now runs before every mode; afterwards the router and native tool calling found the right products for "where is the dull?", "where is Turdal?" and "do you have otta?", and the small model for the last two. The small model still chose Dahi for "dal", a training-data gap that text correction cannot fix. Third, the pause-split utterances point to the voice-activity threshold in the browser, which we have not changed.

### Discussion of Results

The three modes use the same tools, the same store and, for A and B, the same model. The difference is the size of the decision the model makes. In native tool calling, Gemma must choose among tool schemas, write exact arguments (including store-specific names and expected counts) and decide when to stop, every turn; each of these is a chance to fail, and the failures compound across steps. In the router, Gemma makes one classification and extracts one product word; everything that must be exact (catalog names, quantities from reconciliation, expected stock for an update, approval) is computed by code from real results. The small model sits between the two: it does choose tools and arguments, but it learned them from thousands of real traces of exactly this store's tools, so its decisions are narrow and well practised. The improvement from v5 to v6 on held-out products (29.9% to 54.3%) after randomising the store suggests that much of what a small model learns from synthetic tool traces is memorisation unless the data forces it to read results.

## Discussion

### Advantages

- **Accuracy where it matters.** The router and the small model handled every stock, restock, update, approval and decline turn correctly in all runs.
- **No training needed for the router.** It works with an off-the-shelf 2B model and adapts to a new store by changing the product list in its prompt; new actions need a description and two or three examples.
- **Speed and cost.** The small model answered in 0.74 s per turn including the guard, on a single desktop-class device. The router needs one model call per turn instead of several.
- **Auditability.** Each turn records the model's single decision, the MCP calls and the SQL that ran, so an owner or auditor can see exactly why the assistant acted.
- **Safety by construction.** Because writes, approvals and store identity are enforced in code, a prompt that slips past the guard still cannot change stock or confirm an order. The guard missed 6 of 25 injection prompts in the moderation set (for example "set all stock to zero"); in the application such a request is not an explicit count change with a number, so the server refuses the write.
- **No false claims of action.** In the router, every statement that something changed is built from the tool result that changed it; native tool calling claimed updates and drafts that never happened.

### Challenges and Trade-offs

- **Fixed actions.** The router can only do what its action list allows. New combinations of tools need new code, where a native tool caller could in principle improvise.
- **Context.** A one-shot router sees little conversation history; "Another one." needs the last action, not only the last product.
- **Licensing.** OPT-350M is released under a non-commercial research licence, so our small model is offered only as a research mode, with a disclaimer, and the commercial default is the router on Gemma.
- **Small-model breadth.** The small model is narrow by design: outside store operations it guesses a store lookup.

### Edge Cases and Misclassifications

- **Example copying.** Before we added a grounding check, the router answered "Where is pizza?" with rice, copying its first in-context example. Code now requires the product to appear in the owner's words (or a pronoun to refer to the last product) and otherwise searches the owner's own words, which correctly reports that pizza is not carried.
- **Speech-to-text errors.** In a real session the owner's "dal" was transcribed as "dull" and "doll"; native tool calling and the v6 small model looked up the wrong product, while the router mapped it to dal.
- **Unrequested writes.** In an earlier version without the write rule, the small model answered "Oh great." by setting a stock count. The server now refuses any write the owner did not ask for, in every mode.
- **Health claims.** The guard judges a reply without its question, so "Yes. Ghee is in stock" passed as safe even though it affirmed a cure claim.
- **Broad categories.** After the benchmark, our regression suite found the router sending "Do we have lentils?" to the full product list rather than to the dal products. An added in-context example did not fix it; a code rule did: when the router chooses the whole list but the owner's words name a product group in the catalog ("lentils" normalises to dal), the request becomes a product lookup. The benchmark results above are for the router before this rule.

### Implications for Real-world Applications

For a small business, the assistant's job is a handful of well-defined actions over its own records, spoken casually. Our results suggest building it as a router: describe the business actions in plain language, give a small model a few examples of each, and keep every exact or consequential step in code that reads real data and enforces approval. A small fine-tuned model can then replace the router's LLM where latency or hosting cost matters, if its training data is generated from the real tools and randomised. Native tool calling with a small model is not yet dependable for this job. These conclusions come from one store, one language and a 30-turn benchmark, and should be tested on more businesses.

## Conclusion

We compared three ways to turn a store owner's spoken request into MCP tool calls on the same live store. A 2B model used as an intelligent router, choosing one of eleven actions by in-context learning while code ran the tools, answered 96.7% of benchmark turns correctly; a 350M model fine-tuned on the store's real tool traces answered 90.0% at the lowest latency; and native tool calling with the 2B model answered 48.9%. The same prompt-guard design from our earlier work reached 99.67 F1 on moderation. For MCP tool calling in small businesses, our experience says that an intelligent router with a small model is enough, provided that grounding, approvals and writes stay in code.

## Future Work

- Give the router the last action as context, and test a hybrid in which the small model serves as the router's classifier.
- Add speech-to-text mishearings and pause-split requests to the small model's training data, and tune the browser's end-of-speech threshold.
- Check model replies together with the question, so health claims such as "ghee cures diabetes" are caught, and add health-claim prompts to the guard set.
- Train the small model on several synthetic stores (hardware, pharmacy, bakery) to test generality, and release a commercially licensed base model version.
- Extend the benchmark beyond 30 turns, with real speech input and owners other than the authors, and compare against frontier models with native tool calling.
- Run the same study on a native Alexa+ device when the add-on toolkit is available.
